## 3. SGLang 接入 Mac（MLX runtime）

**过程**
- 用户问 vLLM/SGLang 能否在 Mac 跑 → 调研确认：**SGLang 官方支持 Apple Metal**（MLX runtime，`SGLANG_USE_MLX=1`），vLLM 当时无官方支持
- 按官方文档源码安装：clone sglang master → 换 pyproject（`srt_mps` extra 在 `pyproject_other.toml`）→ 独立 venv `.venv-sglang` 安装
- 用 Qwen3-0.6B-4bit 验证：启动 → OpenAI API → 项目 `SGLangAdapter` 全接口（models/completions/stream/metrics）

**遇到的问题与解决**
| 问题 | 解决 |
| --- | --- |
| PyPI 版 sglang 0.5.2 无 `srt_mps` extra（Apple Metal 只在 master） | 从源码安装 |
| 构建需要 Rust（cargo）编译扩展 | `SGLANG_BUILD_RUST_EXTS=none` 跳过 |
| 无完整 Xcode（只有 Command Line Tools），sgl-kernel 原生 Metal kernel 无法编译 | 文档标注可选，MLX runtime 不依赖它 |
| SGLang metrics 默认关闭 | `--enable-metrics` 后 `/metrics` 挂在服务主端口 |
| 沙箱限制 `~` 写入 | venv 与缓存全部指向工作区内（`.venv-sglang`、`UV_CACHE_DIR`） |
| 引擎在独立 venv，项目如何启动它 | 新增 `engine_python` 配置字段 + `sglang_use_mlx` 标志 |

**产出**：`configs/serve/sglang_mac.yaml`、`src/minillm/serve/{config,launch}.py` 扩展、`tests/test_launch_sglang.py`、docs/serving.md Mac 章节

## 5. 同机三引擎压测对比

**过程**
- 方案讨论（用户确认）：**统一 Qwen3-0.6B 原始 fp16 权重** + **三引擎串行隔离**（统一内存带宽是共享资源）+ 先冒烟后全量
- 下载原始权重（1.4GB，hf-mirror）→ 三引擎逐一冒烟 → 编写编排脚本 `scripts/bench_mac.py` → 全量矩阵（并发 1/4/8 × 输入 32/256 × 输出 32/128）

**结果**（并发 8，in=256/out=128）
| 引擎 | c=1 | c=4 | c=8 | 结论 |
| --- | --- | --- | --- | --- |
| **vLLM-MLX** | ~150 | ~250 | **~480 t/s** | 近乎线性扩展，稳定 100% |
| **SGLang-MLX** | ~155 | **~440 t/s**（调参后） | ❌ Metal OOM | 单点最强，高并发缺陷 |
| **HF** | ~40 | ~27 | ~14 t/s | 反向下行，E2E 延迟爆炸（64s） |

**遇到的问题与解决**
| 问题 | 解决 |
| --- | --- |
| SGLang 并发 4 即失败（成功率 25%→0%） | 查日志确诊 **Metal OOM**（`kIOGPUCommandBufferCallbackErrorOutOfMemory`）：默认 `mem_fraction_static=0.88` 过激 → 降到 0.6 并发 4 恢复（并发 8 仍 OOM，属 MLX 后端缺陷） |
| 冒烟时 8000 端口被旧 hf 服务占用 | 清理端口后重启 |
| 全量矩阵 40 分钟 | 后台运行 + 脚本化编排 |

**产出**：`scripts/bench_mac.py`（引擎自动启停/压测/汇总）、`docs/benchmark-results.md`、README 实测数据表更新

## 6. venv 管理讨论

**过程**
- 用户问"有必要合并 venv 吗"、"uv 管理下三个 torch 是否共享"

**结论（实测验证）**
- 三个 venv（945M + 1.6G + 1.7G）的 torch **inode 各不相同** → 是独立副本
- uv 缓存只保证**不重复下载**，安装到每个 venv 仍是独立解压副本
- **不建议合并**：功能零收益（引擎独立进程 + HTTP 通信）、vLLM/SGLang/主项目三方依赖约束冲突（setuptools/numba/fastapi 等锁死）、平台差异（mlx vs CUDA）
- 已共享的部分：模型缓存（HF_HOME）、依赖下载缓存（UV_CACHE_DIR）

## 9. 运行问题排查

**① ulimit 警告（fd 限制）**
- 现象：vLLM 启动警告 `Found ulimit of 2048 ... Consider increasing with ulimit -n`
- 排查：`launchctl limit maxfiles = 256/unlimited`，`kern.maxfilesperproc=92160`
- 解决：启动前 `ulimit -n 65536`（临时）/ `~/.zshrc` 加一行（持久）；低并发可无视

**② "Repo id must be..." 启动报错**
- 现象：`minillm serve` 启动 vLLM 报 transformers hub 错误，把本地路径当 repo id
- 排查：**根因是 git-filter-repo 清理大文件时把磁盘上的 `data/models/Qwen3-0.6B-4bit/` 目录也删了**，配置仍指向它 → transformers 找不到本地目录就尝试当 hub repo
- 解决：vllm_mac.yaml / sglang_mac.yaml 改用仍在磁盘的**原始 fp16 权重**（`data/models/Qwen3-0.6B`）；想用 4bit 需重新下载（gitignore 已覆盖不会入库）；同步修测试断言

**③ max_len 探测脚本的两个 tokenizer 坑**
- 现象：构造 N-token prompt 后服务端只收到约一半（1000 → 501）
- 根因 1：**BPE 词表含 `" token"`（带前导空格）类合并 token**，重复文本 re-tokenize 被压缩
- 根因 2：`decode` 默认 `clean_up_tokenization_spaces=True` 压缩空格
- 解决：超量构造 + token 空间截断 + 本地精确计数、以服务端回显为准
- 实测结果（vLLM-MLX, max=8192）：**边界 8183**（8183 prompt + 8 template + 1 输出 = 8192 ✓），8184 → 400 精确报错

**产出**：`scripts/test_max_len.py`（二分探测 + 边界确认）、`tests/test_max_len_script.py`、实测报告
